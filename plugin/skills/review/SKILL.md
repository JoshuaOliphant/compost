# Review

A change that passes its tests can still break the repo's rules or quietly miss what the issue asked for. Review catches both before the change reaches `compost:finish`. Subagents do the reviewing so the reviewer never shares the author's context, and each finding has to survive a skeptic before it costs you a fix. On a diff that changes executable code, the harness's own code review runs alongside them as a second opinion on correctness.

Run this after `compost:verify` passes on every issue. Nobody needs to ask.

## Steps

1. **Run the review workflow.** Run `/compost:review-changes` with `{base, head, issue, jev: "${CLAUDE_PLUGIN_ROOT}/scripts/jev.py"}`. Leave `base` out to review against the merge-base with the default branch. Leave `head` out to review up to `HEAD`; pass it to review one issue's commits on a branch that has moved on, such as `<merge>^2` for an issue landed by a merge. Pass `issue` when you know the issue, as the tracker writes its id (`42`, `bd-a1b2.3`, `group/project#12`, `OLI-66`), since the Spec axis needs its AC-N. When the tracker is read through tools (an MCP tracker such as Linear), fetch the issue and comments yourself and pass the text, headings and all, as `spec`. The workflow scopes the diff and ranks the changed files by structural risk with Jev's `review-risk`, so reviewers read the riskiest first. It runs a Standards reviewer and a Spec reviewer as `compost:reviewer` subagents in parallel (one reviewer on both for a small diff, below); each picks its canon essays, anchors its findings, and grades their severity with Jev ([Jev tools](references/jev-tools.md)). A skeptic told to refute it gets each finding Jev marks worth one: a probable blocker or major, or a call Jev is unsure of. The rest come back marked unverified. When Jev is unavailable, the reviewers grade severity themselves and every blocker and major gets a skeptic, while minor findings skip it. Pass `skeptics: 3` for a branch where a false finding would be expensive; a finding then survives only when most votes cast uphold it (a tie refutes).

   On a later round, pass `since` as the latest `Review round` comment's `Head:` line and `prior` as its `Findings and rulings` list, verbatim. Reviewers then judge only what changed since that head, and a ruled finding stays ruled unless its code changed. With no `Head:` line (an older comment), or a `since` that no longer resolves or is not an ancestor (a rebase; `delta.problem` says so), the whole branch is reviewed; say so in step 6.

   Every change gets this review, whatever its size. Size picks the path, never whether review runs: a diff of 50 changed lines or fewer (insertions plus deletions from `git diff --shortstat`) that Jev ranks and finds not structural gets one `compost:reviewer` on both axes. The workflow splits its findings by axis (`path` says `light`). Without Jev's ranking, the diff gets two reviewers. Pass `full: true` to force two reviewers.

   Every reviewer, on either path, returns `checked` beside its findings: what it read, each at a `file:line`, and on Spec one entry per AC-N with its verdict. The workflow fails an axis whose reviewer cites no `file:line` or, on Spec, leaves some AC-N of the spec out of both a cited entry and a finding's claim (evidence does not count), because an empty findings list with nothing behind it is a reviewer that did not look, not a clean diff. That counts every `AC-N` in the spec text, including another issue's it quotes ("keeps #12's AC-3 working"); it errs toward incomplete on purpose, so map it on the re-run below or say in the comment why it doesn't apply. A failed axis still returns its findings, skeptic verdicts and all; take them through step 3, and keep them when the re-run misses them.

   Running the workflow from this skill is the opt-in it needs: it spawns a handful of agents, not dozens. If the Workflow tool is unavailable (as inside a subagent) or the system denies its call (auto mode can refuse it), do the same by hand, and say in the step 6 comment that the review ran by hand and why: run `review-risk` yourself, spawn two `compost:reviewer` agents in one message, one per axis, each given the ranked files and the review guide (the base's `REVIEW.md` and standards, read with `git show <base>:<path>`, else the defaults in [the starter](../setup/references/review-md.md)) and told to return `checked` as above, drop what they raise in skipped files and cut minors past the cap, then one skeptic pass (`compost:skeptic` agents, run per [skeptics by hand](references/skeptic-by-hand.md)) over the findings whose `skeptic` is true, else every blocker and major. The skeptic pass and the harness code review below are part of the review, not extras to drop on this path. Tell the Spec reviewer which repo the diff is in (the owner/name in `git remote get-url origin`), and check each `elsewhere` entry by the workflow's rule (below) before you count it. When the diff meets the light criteria above, spawn one agent on both axes instead, told to tag each finding with its axis and return `checked` per axis, and split its findings by axis before the skeptic pass. A denied call is not a skipped review, and the fallback is this procedure, not a retry. If the user themselves declined the call, stop and ask them.

   If the workflow reports an empty diff or an unresolvable base, fix that first: commit the work, or pass the right base. If it skipped the Spec axis because no spec was found, say so in the issue comment in step 6. A change reviewed on one axis has been half reviewed.

   If `complete` is false or an axis's status starts with `failed:`, the review did not happen; `problem` says why. Fix what it names (an unfetchable issue, a reviewer that did not return) and run the workflow again, or the by-hand fallback for that axis with its prompt naming what the last reviewer left out; a by-hand reviewer whose `checked` cites no `file:line`, or skips an AC-N, has not reviewed either. If the axis is still incomplete, the step 6 comment and any PR note say so and on which axis, never that it found nothing. Never move on to `compost:finish` from an incomplete review.

   A spec can span several repositories. The Spec reviewer lists each elsewhere criterion (an AC-N the spec places in another repo, on its defining line before its id or in a heading over it, under a name that is not this repo's) under `elsewhere`; the workflow refuses an entry the spec does not back that way, leaving the AC-N unmapped and the axis failed. Accepted ones come back in `spec.elsewhere` and the Spec status. They are not met by this review: the step 6 comment lists each with the repo whose review covers it (or "not yet reviewed"). When the spec names no repo for criteria you know live elsewhere, fix the spec and review again rather than ruling the findings away.

   Each axis also returns `preExisting`: real bugs at lines the diff did not change (one graded `pre-existing` at a changed line is judged as a major instead). They never block: don't verify or fix them here, which would widen the change; step 6 records them. The result's `guide` names the review guide (the base's `REVIEW.md` or the defaults): findings in files it skips are dropped, and minors past its cap are cut. Its `## Checks` come back in `checks`, each `triggered` or `not triggered` with why; Standards fails when its `checked` cites no `file:line` for a triggered one.

   Each axis also returns an `unjudged` list: findings sent to a skeptic whose skeptics all failed, so nobody tried to refute them. Treat every unjudged finding as a survivor in the steps below.

   **Run the harness's built-in code review too, when the diff changes executable code.** Executable means scripts, hooks, workflows, tests: source in a programming language. A diff of only Markdown, prose, or data has nothing for it to hunt; skip it and say why in step 6. Otherwise, alongside the review (while the workflow runs, or while the reviewers do on the by-hand path), invoke the code review skill that ships with the harness you are running in: `code-review` in Claude Code (not a plugin's skill of a similar name), `/review` in Codex. It hunts correctness bugs, which neither axis is built to find. Point it at the same range (in Claude Code, the branch as its target, or nothing for the working diff), without `--fix` or `--comment`: its findings go through step 3 like the others, and nothing is posted unchecked. When the harness ships no such skill, or it fails, note that in the issue comment in step 6 and carry on; the two axes are still the review that gates `compost:finish`.

2. **Keep the two axes apart.** Read the Standards and Spec survivors side by side. Don't merge them into one ranked list: code can follow every standard and still build the wrong thing. Keep the built-in review's findings as a third list for the same reason; it has run its own verification, so treat each as a survivor. Skim the refuted lists too. When a skeptic refuted a blocker with reasoning you can see is wrong, check the code yourself and treat the finding as a survivor if it holds.

3. **Verify each survivor against the code before you act on it.** A survivor is a claim, not an order. For each one:
   - Restate what it asks for in one line, in the domain's terms.
   - Open the file at the cited line and check the claim against the code, the tests, and the callers. A skeptic's `correction` replaces the reviewer's citation.
   - If it asks for something to be "done properly" (configurable, generalised, more layers), grep for a caller that needs it first. No caller means you push back: the extra code is speculative generality, the thing [subtract before you add](../../canon/subtract-before-you-add.md) warns against.
   - If it contradicts a ruling already logged on the issue, or an ADR, the ruling stands until someone supersedes it. Push back and cite the ruling.

   Push back with evidence, not tone: the file:line that shows the reviewer wrong, the test that covers it, the missing caller. When a finding is right, fix it and say what changed. Skip "good catch" and "you're right"; the fix shows you heard it. When you pushed back and then find you were wrong, say so in one line and fix it.

4. **Fix the survivors that hold, one at a time.** Blockers first, then the quick fixes, then anything that reshapes code. Fix at the root ([fix root causes](../../canon/fix-root-causes.md)), and when a fix replaces an interface, replace it: the old code goes in the same change, with no shim left behind. After each fix that changes behaviour, run the tests that cover it. When a Standards survivor is mechanical (a banned API, an import shape, a file in the wrong place), fix the instance and also file an issue for a lint rule, hook, or CI check that would have caught it ([make mistakes impossible](../../canon/make-mistakes-impossible.md)). A judgement survivor a diff can show gets a proposed `REVIEW.md` check ([shape](../setup/references/review-md.md)) citing this issue as Source; the user adds it (unattended: a ruling).

5. **Re-verify.** Once the fixes are in, run `compost:verify` again in full: suite, gates, the AC-N map. If the fixes changed behaviour or touched files the first review didn't see, run the review again, the same way step 1 ran it (workflow or by hand), with `since` and `prior` from this round as in step 1, and the built-in review once more when the diff changes executable code. A finding you pushed back on that comes back from a fresh reviewer deserves a second look, not a second refusal by reflex.

6. **Record the outcome on the issue.** Post one comment, headed `Review round <n>` (one more than the issue's earlier review comments; `compost:implement` counts these for its three-round cap). The next round reads back two parts, so keep their shape: a `Head: <sha>` line, the head the last workflow run of this round reviewed (its result's `head`), and a `Findings and rulings` list, one line per finding: severity (with `reviewerSeverity`, `unsure` or `movedFrom` when set), file:line, claim, and the ruling (fixed in <commit>, pushed back: <reason>, or pre-existing). Around them, write what each axis and the built-in review found, with what each axis checked (for a clean Spec axis, each AC-N and its verdict), the evidence behind each pushback, whether the Spec axis and the built-in review ran, each elsewhere criterion with the repo whose review covers it, the `guide` used and how many minors its cap cut, each triggered check's answer, and whether the review ran by hand and why. That comment is the ruling log `compost:finish` summarises into the PR.

   When the guide was the defaults and no earlier review comment on this issue has a `REVIEW.md offered` line, offer once to write one from [the starter](../setup/references/review-md.md), seeded with the files the review skipped and what you pushed back on as noise, and add that line. Unattended, put the proposed text under that line instead of writing the file.

## When the branch is structurally risky

Standards and Spec both judge the change against a reference. Neither asks whether the approach itself was the right one. For a branch that adds a module boundary, a new data flow, a new external dependency, shared or global state, or a change that crosses bounded contexts, have a separate agent judge approach fit. This is opt-in: most issues don't need it.

The trigger is the workflow's `risk.structural`: run approach fit when it is true, and keep the flagged file names out of the problem statement, since they hint at the mechanism. When `risk.ranked` is false (`risk.problem` says why), decide from the list above by reading the changed files. The flag misses about one structural file in seven, so a branch you can see adds one of those things still gets the judge.

Write a problem statement that describes only the problem, never the solution: what should work differently afterward, or what is broken. Any hint about the mechanism biases the judge toward the code it is about to read. Then spawn one subagent with the prompt in [approach fit](references/approach-fit.md). Treat its verdict like a survivor from step 3: verify it, and if it names a better approach you agree with, hand the design question to `compost:deepen`.

For a large or ambiguous change, `vet` is a further independent pass over the diff and the conversation. Use it when the scope is wide enough that two focused reviewers could miss something between them.

## When the user wants to sign off themselves

Some changes the user wants to read with their own eyes. When they say so, follow [review-diff](references/review-diff.md). It opens the branch diff in a local browser for inline, merge-request style comments and waits while they review. Their comments are the user's own review: understand each, ask about anything unclear before changing code, then fix, re-verify, and record them on the issue as in steps 4 to 6.

## Next moves

- `compost:finish` when the review came back complete, no survivors or unjudged findings remain, and verify passes.
- `compost:verify` after any fix, before you call the review done.
- `compost:diagnose` when a finding exposes a defect whose cause you can't see from the cited line.
- `compost:deepen` when approach fit, or a cluster of Standards findings in one module, says the design is the problem.
- `compost:build` when a Spec finding shows an AC-N that was never built.
